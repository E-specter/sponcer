# Auditoría F4-E2E: pruebas E2E y accesibilidad contra el stack real local

**Responsable humana:** Mariana · **Auditor:** agente audit (independiente de los devs)
**Casos:** E2E-01 a E2E-09 + accesibilidad (axe WCAG 2.1 AA, teclado) · **RF/RNF:** RF-01 a RF-13, RNF-03, RNF-05

## Resultado: **OBSERVACIONES** (ver "Re-verificación" al final: **APROBADO**)

Los nueve flujos pasan de punta a punta contra Supabase, backend y frontend reales. No se encontró ningún defecto de seguridad (RLS, aislamiento, rate limit). Hay **3 defectos funcionales/de diseño** (B-01 a B-03), ninguno bloqueante para la demo, y 4 observaciones menores.

Suite: **56 tests, 56 pasan** (3 de ellos son `test.fail` sobre defectos conocidos; se marcan `x` en el reporter `list` pero cuentan como esperados). Dos corridas seguidas idénticas, ~1,4 min. Sin datos residuales en la BD tras la corrida (0 perfiles, usuarios ni pedidos con prefijo `e2e`).

## Cómo ejecutar

Stack (puertos distintos de los de desarrollo para no chocar):

```bash
# Supabase local ya arriba (API 55521, Mailpit 55524) con `npm run db:reset` hecho
cd backend  && PORT=3100 CORS_ORIGIN=http://localhost:4421 npx tsx --env-file=.env src/main.ts   # ADAPTER_* real, INGESTION=mock
cd frontend && PUBLIC_API_URL=http://localhost:3100 PUBLIC_API_MODE=http PUBLIC_AUTH_MODE=supabase npx astro dev --port 4421
cd frontend && npx playwright install chromium   # una vez
cd frontend && npm run e2e                       # o: npx playwright test e2e-06   /   npx playwright test a11y
```

`frontend/playwright.config.ts`: `testDir tests/e2e`, `baseURL` 4421 (`E2E_BASE_URL`), 1 worker (comparten BD), sin `webServer` (el stack se levanta a mano). Las credenciales de Supabase se leen de `backend/.env` y nunca se imprimen; **los E2E se niegan a correr si `SUPABASE_URL` no es local**.

## Diseño de la suite

- **Datos aislados:** cada spec crea usuarios `e2e-<tag>@e2e.sponcer.local` y handles `e2e.<tag>`, y los borra en `afterAll` (también barre restos de más de 10 min). Los perfiles sembrados solo se leen.
- **Login:** E2E-01 usa el camino real (formulario → correo en Mailpit → enlace → callback PKCE). El resto crea la sesión con `auth.admin.generateLink` + `verifyOtp` con el mismo cliente SSR que usa la app, y deja las cookies httpOnly en el contexto de Playwright (son las cookies exactas de la app). Las sesiones se cachean para no agotar el límite de verificaciones de Supabase (30/5 min).
- **Preparación vs acción:** la preparación (reclamar perfiles, crear matches) usa la core API; la **acción bajo prueba siempre va por la UI** o, en E2E-08, por peticiones directas con el token del usuario.
- **Hidratación:** las islas de Astro se hidratan después del HTML; `visit()` espera a que no queden `astro-island[ssr]` (si no, `fill` se pierde).
- **Límite de tasa:** `POST /claims` está limitado a 30/min por IP; una suite rápida lo alcanza. `apiAs().call` reintenta ante 429 (esperas de 4 s). Es a la vez evidencia de que el rate limit funciona.

### Observaciones menores (sin test que falle)

- **O-1 (baja, UX):** las tarjetas del feed no ofrecen "Solicitar cotización" (RF-10 lo lista entre las acciones por tarjeta); solo está en la ficha del creador.
- **O-2 (baja, UX):** un pedido de exclusión del titular sin cuenta sobre una ficha sin reclamar queda `pending` (revisión manual) y la ficha sigue visible; el formulario dice "Te escribiremos al correo indicado" pero no hay herramienta ni plazo para esa revisión. Coherente con el diseño del caso de uso; falta el proceso.
- **O-3 (info):** con `ADAPTER_INGESTION=mock` la lista de bloqueo es en memoria (no escribe `ingestion_blocklist`); su efecto se verifica (no se puede re-reclamar) pero no la fila en BD. Con `apify` conviene repetir esa aserción.
- **O-4 (info):** el ranking de un perfil recién creado se estabiliza unos instantes después de declarar datos (la clasificación y el embedding son asíncronos): un feed pedido de inmediato no incluye `niches`/`similarity` entre los motivos. Los tests esperan a que haya clasificación o no dependen de ello.

## Seguridad y privacidad observadas

- **RLS (E2E-08):** caso permitido (participantes leen) y denegado (tercero y anónimo reciben `[]`, no pueden insertar) comprobados por PostgREST con token real, por la API y por Realtime.
- **Rutas protegidas:** `/descubrir`, `/perfil`, `/panel`, `/mensajes` redirigen a `/login` sin sesión; la ficha previa no se filtra en el cuerpo del 302.
- **Cookies de sesión:** `httpOnly`, `SameSite=Lax` (sin `Secure` en http local, correcto).
- **Rate limit:** `POST /claims` responde `429 RATE_LIMITED` al superar 30/min por IP (observado); `requestRemoval` limita a 20/h (no se superó).
- **Aviso de prueba:** el limitador de exclusiones (20/h por IP) es compartido; correr la suite muchas veces por hora puede agotarlo (cada corrida usa 3).

### Cómo correr lo que necesita configuración
- **Admin:** arrancar el backend con `ADMIN_EMAILS=e2e-admin@e2e.sponcer.local` (por entorno del proceso; no se toca `backend/.env`). El correo se cambia con `E2E_ADMIN_EMAIL`.
- **Demo:** arrancar el frontend con `PUBLIC_DEMO_LOGIN=true DEMO_PASSWORD=E2E-demo-Passw0rd!` (`E2E_DEMO_PASSWORD` lo cambia). El test fija esa contraseña en `usuario4@sponcer.local` y **al terminar la reemplaza por una aleatoria**: el seed la dejaba vacía y no se puede restaurar vacía por la API admin (el acceso por enlace mágico no la usa). Quien necesite esa cuenta con otra contraseña debe volver a fijarla.
- **Navegadores:** `npx playwright install chromium firefox webkit`; `npx playwright test --project=firefox` filtra por motor.
- **Visual y E2E a la vez no:** Astro 7 permite un solo `astro dev` por proyecto; detener el frontend 4421 antes de `npm run e2e:visual`.
- **Límite de exclusiones:** `POST /removal-requests` admite 20/h por IP. Una corrida de 3 navegadores consume ~9; varias corridas seguidas agotan el límite y fallan E2E-09 con 429. Reiniciar el backend lo restablece.

### Hallazgos por motor
- **Solo Firefox, 2 tests saltados:** al correr axe sobre `/descubrir` a 1440 px, Firefox cierra la página ("Page crashed"). Se reproduce siempre y se acota a la regla `aria-allowed-attr` sobre `.side-nav` y `.context-panel` (secciones `aria-labelledby` "Tus nichos" y "Novedades"); las demás reglas, otros anchos y otras pantallas pasan y la página funciona con normalidad en Firefox (los 71 tests de flujo pasan). No se determinó si es defecto de Firefox o de axe; **O-6 (media-baja):** conviene que dev-frontend lo mire con Firefox real.
- **Solo WebKit, 2 tests saltados:** Tab no enfoca enlaces (comportamiento de Safari sin Alt+Tab); no es del producto.
- **Ajustes de tests por motor (no del producto):** WebKit reporta `SameSite=None` en su API de cookies para una cookie Lax (el atributo real lo fija el servidor); las cookies de prueba ahora son host-only (`url`), como las de la app; el logout se espera antes de pedir otra ruta.
